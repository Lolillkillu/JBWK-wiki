Firmware

Keyboard firmware frameworks, RTOS, bootloaders and hardware abstraction

Terminology note
Firmware is software stored in a device's non-volatile memory (flash/ROM) that directly controls its hardware. It is typically written in a compiled language such as C — a low-level, general-purpose language that compiles directly to machine code, making it well suited for microcontrollers with limited resources.

A library is a collection of reusable functions that the developer calls from their own code. A framework, by contrast, owns the program's execution flow and calls the developer's code at defined points — a principle known as Inversion of Control (IoC).

TMK, QMK, and ZMK are strictly firmware frameworks: they provide the full program skeleton (matrix scanning loop, USB HID stack, debouncing logic) and invoke the user's keymap at specific lifecycle events. When the framework's C source is compiled by a toolchain (e.g. avr-gcc, arm-none-eabi-gcc) and the resulting binary is flashed onto the MCU, that binary is the firmware. The projects therefore occupy a dual role: they are frameworks for building firmware and, once compiled and flashed, they constitute the firmware itself.

Keyboard Firmware Frameworks

  • TMK The original open-source keyboard firmware framework by tmk. Written in C, it supports AVR and ARM MCUs. TMK owns the main loop — it initialises peripherals, scans the key matrix, runs debouncing, and handles USB HID communication. The user only fills in the keymap array; the framework calls that data at scan time. This Inversion of Control makes TMK a framework, not a library. It is the foundation from which QMK was forked.
  • QMK Quantum Mechanical Keyboard — a feature-rich firmware framework forked from TMK. Written in C, it extends TMK with dynamic macros, RGB lighting control, mouse keys, an extensive keycode system, and the qmk CLI build tool. Like TMK, it uses Inversion of Control: the framework's scanning loop calls the user-defined keymap. QMK source is compiled by avr-gcc or arm-none-eabi-gcc into a binary that is flashed as firmware onto the MCU. It is therefore a firmware framework, not a library, and not firmware in isolation — only the compiled binary flashed to hardware is firmware.
  • ZMK A modern, wireless-first keyboard firmware framework built as an application on top of the Zephyr RTOS. Written in C. Zephyr itself acts as the OS/runtime layer; ZMK is the framework that specialises Zephyr for keyboard functionality. Hardware configuration uses Devicetree overlay files (.overlay); keymaps are defined in Devicetree-format .keymap files — not YAML. Supports BLE, split keyboards, and low-power operation. Built and flashed via the west build tool.

Real‑Time Operating Systems (RTOS)

  • Zephyr A scalable, open-source RTOS hosted by the Linux Foundation. Provides a rich driver model, a Devicetree-based hardware description system, Kconfig build configuration, and support for over 500 boards. Used in industrial, IoT, and consumer embedded devices. ZMK runs on top of Zephyr as an application framework.
  • ChibiOS A compact, high-performance RTOS targeting ARM Cortex-M microcontrollers. Includes a Hardware Abstraction Layer (HAL), a TCP/IP stack, and a FAT filesystem. Known for its efficient interrupt latency and small flash/RAM footprint. Used by QMK on certain ARM-based keyboards.

Bootloaders

  • DFU / USB‑DFU Device Firmware Upgrade — a USB standard that allows a device to receive and write a new firmware binary over USB without an external programmer. The bootloader is a small piece of firmware itself, stored in a protected memory region, that runs before the main application and checks for an incoming update. Widely used on STM32, nRF52, and ATmega32U4 MCUs.
  • U‑Boot A widely-used open-source primary bootloader for embedded Linux systems. Supports multiple filesystems, network (TFTP) boot, and verified/secure boot. Typically used on higher-end ARM and RISC-V application processors (e.g. i.MX, Allwinner, Rockchip) rather than the bare-metal MCUs used in keyboards.

HAL & Peripheral Drivers

  • Hardware Abstraction Layer (HAL) A layer of C code, typically provided by the silicon vendor (e.g. STM32Cube HAL, NXP MCUXpresso SDK), that exposes a uniform API for peripherals such as GPIO, UART, SPI, I²C, and DMA. HALs are libraries in the strict sense — the developer calls their functions. They make firmware more portable across device families without rewriting low-level register code.
  • Timer & PWM Hardware timers in MCUs are used for accurate delay generation, frequency measurement, and periodic task scheduling. PWM (Pulse Width Modulation) is generated by configuring a timer's compare channel to toggle a GPIO at a defined duty cycle — essential for controlling motor speed, LED brightness, and audio output.
